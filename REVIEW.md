# Ревью API бронирования

Ревью `app/Http/Controllers/BookingController.php`. Методы `index` и `today` по условию задания не исправляются, но разобраны здесь вместе с остальными.

## Сводка

| Severity | Количество |
| --- | --- |
| Critical | 6 |
| Major | 7 |
| Minor | 7 |

## Critical

### C1. SQL-инъекция в `store`

**Где:** `store()`, вызов `DB::select(...)`.

**Проблема:** значения из запроса интерполируются прямо в SQL:

```php
$conflict = DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");
```

`room_id` подставляется без кавычек, даты — внутрь строковых литералов. Кавычка в дате или выражение в `room_id` меняют запрос. Это позволяет читать и изменять произвольные данные от имени приложения.

**Как исправить:** сначала валидировать вход, затем строить запрос через Eloquent/query builder с bindings:

```php
$conflict = Booking::query()
    ->where('room_id', $request->integer('room_id'))
    ->where('starts_at', '<', $endsAt)
    ->where('ends_at', '>', $startsAt)
    ->exists();
```

### C2. Автор брони берётся из запроса

**Где:** `store()`, `Booking::create($request->all())`.

**Проблема:** `user_id` входит в `#[Fillable(...)]`, поэтому клиент сам назначает автора. Пользователь Борис может создать бронь от имени Анны, и в `today()` она будет показана как бронь Анны.

**Как исправить:** автора брать только из аутентификации:

```php
$booking = $request->user()->bookings()->create($data);
```

`user_id` не должен приниматься из запроса. В `$data` оставить только `room_id`, `title`, `starts_at`, `ends_at`.

### C3. Любой пользователь может отменить чужую бронь

**Где:** `destroy()`.

**Проблема:** `Booking::findOrFail($id)->delete()` не проверяет владельца. Любой авторизованный пользователь удаляет любую бронь по id — классический IDOR. Требование «отменить бронь может только её автор» не выполняется.

**Как исправить:** проверять автора до удаления — через policy или явно:

```php
$booking = Booking::findOrFail($id);

abort_unless($booking->user_id === $request->user()->id, 403);

$booking->delete();
```

Нужно передавать `Request` в `destroy()` или использовать `$request->user()` через `auth()`.

### C4. Встречи «впритык» считаются пересечением

**Где:** `store()`, условие конфликта.

**Проблема:** используются нестрогие неравенства `starts_at <= ends_at AND ends_at >= starts_at`. Для броней 10:00–11:00 и 11:00–12:00 второе условие даёт `11:00 <= 11:00` и `12:00 >= 11:00`, поэтому возвращается 409 «Комната занята». Требование «10:00–11:00 и 11:00–12:00 — это не пересечение» нарушено.

**Как исправить:** проверять пересечение полуинтервалов строгими неравенствами:

```
starts_at < :ends_at AND ends_at > :starts_at
```

То есть существующая бронь пересекается с новой, только если начинается раньше её конца и заканчивается позже её начала.

### C5. Смещение ISO 8601 теряется и при записи, и при сравнении

**Где:** `store()`, запись `Booking::create(...)` и SQL-сравнение `starts_at`/`ends_at`.

**Проблема:** колонки имеют тип `timestamp(0) without time zone`. Eloquent `datetime`-каст не переводит дату в UTC: он разбирает строку с offset, но при записи форматирует её в «настенное» время и смещение теряет. При чтении значение трактуется как UTC, потому что `config/app.php` задаёт `timezone => UTC`.

Проверено:

```php
$b = new Booking;
$b->starts_at = '2026-11-02T10:00:00+03:00';
$b->getAttributes()['starts_at']; // '2026-11-02 10:00:00'
$b->starts_at->toIso8601String(); // '2026-11-02T10:00:00+00:00'
```

То есть клиент отправил 10:00 MSK (07:00 UTC), а API сохранил и вернул 10:00 UTC — момент времени сдвинулся на 3 часа. Для Новосибирска сдвиг будет 7 часов. Это нарушает требование принимать ISO 8601 с любым смещением: смещение фактически игнорируется.

SQL-проверка конфликта страдает от того же: PostgreSQL для `timestamp without time zone` тоже отбрасывает offset у строкового литерала. Сравниваются «настенные» часы, а не моменты времени.

Примеры:

- существующая бронь создана как `10:00+03:00` и лежит в базе как `10:00`;
- запрос на тот же момент `07:00+00:00` даёт литерал `07:00`, условие `starts_at < '08:00'` для сохранённых `10:00–11:00` ложно — конфликт не найден, создаётся дубль;
- наоборот, запрос `10:00+00:00` (это 13:00 MSK) даёт литерал `10:00` и ложно конфликтует с сохранённой бронью `10:00–11:00`, хотя это разные моменты времени.

**Как исправить:** парсить входные даты в Carbon, приводить к UTC до записи и до сравнения:

```php
$startsAt = CarbonImmutable::parse($request->date('starts_at'))->utc();
$endsAt = CarbonImmutable::parse($request->date('ends_at'))->utc();

// сохранять уже нормализованные значения
Booking::create([
    'starts_at' => $startsAt,
    'ends_at' => $endsAt,
    // ...
]);
```

После `->utc()` Eloquent запишет `07:00` для 10:00 MSK, и все сравнения будут в одной шкале. Альтернатива — перевести колонки на `timestamptz`, но нормализации в UTC достаточно и без смены типа.

### C6. Рабочее время проверяется не в часовом поясе офиса

**Где:** `store()`, проверка `$start->hour < 9 || $start->hour >= 20`.

**Проблема:** `Carbon::parse()` сохраняет смещение, которое прислал клиент, и `->hour` возвращает час в этом смещении. Требование — 09:00–20:00 по местному времени офиса, где находится комната. Таймзона офиса (`offices.timezone`) не используется вообще.

Примеры для комнаты в Новосибирске (`Asia/Novosibirsk`, UTC+7):

- клиент присылает `2026-11-02T03:00:00+00:00` — это 10:00 местного времени, но код видит `hour = 3` и отвечает 422 «Нерабочее время»;
- клиент присылает `2026-11-02T13:30:00+00:00` — это 20:30 местного времени, но код видит `hour = 13` и пропускает бронь.

Кроме того, проверяется только начало. Бронь 19:00–21:00 пройдёт проверку `$start->hour < 20`, хотя заканчивается после 20:00.

**Как исправить:** получить таймзону офиса комнаты, перевести обе даты в неё и проверить весь интервал:

```php
$timezone = $room->office->timezone;
$localStart = $startsAt->setTimezone($timezone);
$localEnd = $endsAt->setTimezone($timezone);

$workStart = $localStart->copy()->setTime(9, 0);
$workEnd = $localStart->copy()->setTime(20, 0);

if ($localStart->lessThan($workStart) || $localEnd->greaterThan($workEnd)) {
    // 422
}
```

Здесь `$startsAt`/`$endsAt` — уже нормализованные UTC-даты из C5. Проверка `$localEnd->greaterThan($workEnd)` одновременно ловит и выход за 20:00, и переход через полночь: конец следующего дня заведомо больше 20:00 текущего локального дня.

## Major

### M1. Входные данные не валидируются

**Где:** `store()`, весь метод.

**Проблема:** нет ни одного правила валидации. В итоге:

- отсутствующие поля дают синтаксическую ошибку SQL или 500;
- `room_id` несуществующей комнаты доходит до INSERT и падает на foreign key с 500;
- `ends_at` раньше `starts_at` создаёт инвертированный интервал;
- не проверяются длительность 15 минут–4 часа и шаг 15 минут: бронь 10:07–10:52 создаётся;
- `title` может быть пустым или длиннее 255 символов;
- произвольная строка вместо даты приводит к исключению Carbon или ошибке PostgreSQL.

**Как исправить:** создать `StoreBookingRequest` со всеми правилами:

- `room_id`: `required`, `integer`, `exists:rooms,id`;
- `title`: `required`, `string`, `max:255`;
- `starts_at`, `ends_at`: `required`, `date`;
- `ends_at > starts_at`;
- длительность от 15 минут до 4 часов;
- минуты кратны 15 и секунды равны нулю;
- `user_id` в правилах отсутствует.

Сообщения — на русском, с привязкой к конкретному полю.

### M2. Конфликт проверяется до валидации, а ошибки отдаются не в том формате

**Где:** `store()`, порядок операций и коды ответа.

**Проблема:** сначала выполняется SQL по сырым данным, потом проверяется рабочее время. Из-за этого:

- невалидный запрос попадает в базу раньше, чем валидация;
- запрос вне рабочих часов может получить «Комната занята» вместо понятной причины;
- конфликт отдаётся как 409 с `{"error": "Комната занята"}`, а требование задания — понятные ошибки валидации 422.

**Как исправить:** порядок «валидация → проверка бизнес-правил → создание». Конфликт возвращать как 422 с полем, к которому он относится, например:

```json
{
  "message": "Комната занята в это время",
  "errors": {
    "starts_at": ["Комната занята в это время"]
  }
}
```

### M3. Двойная бронь при одновременных запросах

**Где:** `store()`, проверка конфликта и INSERT.

**Проблема:** проверка и вставка не атомарны. Два одновременных запроса могут оба не найти конфликт и оба создать бронь. Это бонусное задание, но проблема реальная.

**Как исправить:** обернуть проверку и создание в транзакцию и сериализовать доступ к комнате:

```php
DB::transaction(function () use (...) {
    Room::whereKey($roomId)->lockForUpdate()->firstOrFail();
    // проверка конфликта и создание
});
```

`lockForUpdate()` по строке комнаты работает как мьютекс для всех броней этой комнаты. Как второй рубеж — exclusion constraint из M4.

### M4. На уровне БД нет защиты от пересечений и индекса

**Где:** миграция `create_bookings_table`.

**Проблема:** пересечения контролируются только кодом. Любой другой путь записи (импорт, скрипт, будущий метод) может создать пересекающиеся брони. Индекса по `room_id`/`starts_at` нет, поэтому проверка конфликта будет сканировать таблицу.

**Как исправить:** добавить индекс и exclusion constraint:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE INDEX bookings_room_starts_at_index
    ON bookings (room_id, starts_at);

ALTER TABLE bookings
    ADD CONSTRAINT bookings_no_overlap
    EXCLUDE USING gist (
        room_id WITH =,
        tsrange(starts_at, ends_at, '[)') WITH &&
    );
```

Для `timestamptz` использовать `tstzrange`. Ограничение защищает от гонки на уровне базы, но требует обработки `QueryException` и возврата 422.

### M5. `today` использует день и время UTC, а не офиса

**Где:** `today()`.

**Проблема:** `whereDate('starts_at', today())` сравнивает дату в UTC (таймзона приложения), а не в `office.timezone`. После нормализации дат в UTC (C5) это даст неверные границы дня: бронь в Москве в 01:00 MSK — это `22:00` UTC предыдущего дня, и в «сегодня» она не попадёт. Сейчас, пока offset при записи теряется, поведение ещё и зависит от того, какое смещение прислал клиент: одно и то же локальное время, отправленное как `+07:00` и как `+00:00`, ляжет в разные календарные даты.

Кроме того:

- `$b->starts_at . ' – ' . $b->ends_at` печатает UTC и дату, а не локальное `10:00 – 11:00`;
- `$b->user` в `map()` даёт N+1 запрос на каждую бронь;
- нет сортировки, порядок строк не определён.

**Как исправить:** строить границы дня в таймзоне офиса, переводить их в UTC и фильтровать по `starts_at`, подгружать пользователя заранее:

```php
$timezone = $room->office->timezone;
$dayStart = today($timezone)->startOfDay()->utc();
$dayEnd = $dayStart->copy()->addDay();

$room->bookings()
    ->with('user')
    ->where('starts_at', '>=', $dayStart)
    ->where('starts_at', '<', $dayEnd)
    ->orderBy('starts_at')
    ->get()
    ->map(fn ($booking) => [
        'time' => $booking->starts_at->setTimezone($timezone)->format('H:i')
            .' – '
            .$booking->ends_at->setTimezone($timezone)->format('H:i'),
        'author' => $booking->user->name,
    ]);
```

Код по условию задания не меняем, но в рамках доработки это обязательное исправление, если `today` когда-нибудь тронут.

### M6. Без `Accept: application/json` API отвечает 500 вместо 401

**Где:** `bootstrap/app.php`, `auth:sanctum`, `Authenticate`.


`shouldRenderJsonWhen()` в `bootstrap/app.php` влияет на рендер исключения, но `Authenticate::unauthenticated()` успевает вычислить redirect URL через `route('login')` до рендера. Маршрута `login` нет, поэтому возникает `RouteNotFoundException` и 500. README описывает это как известное поведение, но для API это дефект: клиент должен получать 401 независимо от `Accept`.

**Как исправить:** добавить middleware для группы `api`, который принудительно выставляет `Accept: application/json`, либо обработать `AuthenticationException` в `bootstrap/app.php` и всегда возвращать JSON для `api/*`.

### M7. Непоследовательный контракт ответов

**Где:** `store()`, `destroy()`, `today()`.

**Проблема:**

- `store()` возвращает 200 и сырую модель вместо 201 Created;
- ошибки отдаются в разных форматах: `{"error": ...}`, стандартный `{"message": ...}`, ошибки валидации Laravel;
- `destroy()` возвращает 204 — это корректно, но отмена нигде не логируется (см. N5).

**Как исправить:** вернуть 201 с созданной бронью (при необходимости с `Location`), унифицировать формат ошибок, для бизнес-ошибок использовать 422 и структуру `errors`.

## Minor

### N1. Контекст лога не попадает в `bookings.log`

**Где:** `store()`:

```php
Log::withContext(['booking_id' => $booking->id]);
Log::channel('bookings')->info('Booking created');
```

**Проблема:** `Log::withContext()` через фасад применяется к логгеру канала по умолчанию (`stack`), а `Log::channel('bookings')` — отдельный экземпляр логгера. Поэтому `booking_id` в `storage/logs/bookings.log` не попадёт. Кроме того, контекст остаётся на логгере до конца запроса.

**Как исправить:** передавать контекст прямо в вызов:

```php
Log::channel('bookings')->info('Booking created', ['booking_id' => $booking->id]);
```

### N2. `index` без стабильной сортировки и с сырой моделью

**Где:** `index()`.

**Проблема:** `orderByRaw('starts_at DESC')` не содержит вторичного ключа. Брони с одинаковым `starts_at` могут менять порядок между страницами. Размер страницы зашит в код, параметр `per_page` не валидируется. Отдаётся сырая модель, то есть структура ответа жёстко связана со схемой таблицы.

**Как исправить:** добавить `orderByDesc('id')`, при необходимости — валидируемый `per_page`, при развитии API — Resource. Для текущего задания это не блокирует.

### N3. `today` без сортировки и с пропуском броней через полночь

**Где:** `today()`.

**Проблема:** нет `orderBy`, поэтому порядок не гарантирован. Фильтр `whereDate('starts_at', ...)` учитывает только начало: бронь, начавшаяся вчера и заканчивающаяся сегодня, в выдачу не попадёт.

**Как исправить:** сортировать по `starts_at`; при необходимости учитывать пересечение с днём, а не только начало (см. M5).

### N4. Нечисловые route-параметры дают 500

**Где:** маршруты `DELETE /api/bookings/{id}` и `GET /api/rooms/{room}/bookings/today`.

**Проблема:** проверено: `Booking::findOrFail('abc')` приводит к `SQLSTATE[22P02] invalid input syntax for type bigint`, а не к 404. Аналогично для `{room}`.

**Как исправить:** ограничить параметры числами:

```php
Route::delete('/bookings/{id}', ...)->whereNumber('id');
Route::get('/rooms/{room}/bookings/today', ...)->whereNumber('room');
```

Либо перейти на route model binding `{booking}`.

### N5. Отмена брони не логируется

**Где:** `destroy()`.

**Проблема:** создание пишется в `bookings.log`, удаление — нет. Восстановить историю отмен невозможно. Требованием не запрещено, но для аудита полезно.

**Как исправить:** логировать id брони, автора и время отмены перед удалением.

### N6. Нет ограничения частоты запросов

**Где:** `routes/api.php`.

**Проблема:** на API нет `throttle`. Один клиент может создавать и удалять брони без ограничений. Для демо это не критично, но стандартная практика для публичного API.

**Как исправить:** добавить `throttle:api` или именованный rate limiter.

### N7. `Carbon::parse` принимает не только ISO 8601

**Где:** `store()`.

**Проблема:** `Carbon::parse('tomorrow')`, `Carbon::parse('next monday')` и другие относительные форматы успешно разбираются. Если такой запрос дойдёт до SQL, поведение зависит от того, как PostgreSQL разберёт строку; после добавления валидации это перестанет быть проблемой, но полагаться на `parse()` как на валидатор нельзя.

**Как исправить:** валидация формата в `StoreBookingRequest` (`date` + проверка ISO 8601 при необходимости) до парсинга.

## Подозрительно, но проблемой не является

- **`timestamp without time zone`.** Сам тип не является ошибкой: Laravel хранит даты в UTC. Проблема — в смешивании строки с offset и UTC-значения в SQL (C5), а не в типе колонки.
- **`$request->all()` и `Fillable`.** `Fillable` действительно отсекает посторонние поля, поэтому произвольные ключи не попадут в модель. Но `user_id` входит в список разрешённых, поэтому защита не спасает от подмены автора (C2).
- **Пагинатор в ответе `index`.** Возврат `LengthAwarePaginator` как JSON — рабочий контракт, метаданные пагинации присутствуют.
- **`today` показывает брони всех пользователей комнаты.** Для расписания переговорной это ожидаемо, а не утечка.
- **`findOrFail` и 404.** Для существующего числового id метод корректно даёт 404 через обработчик исключений.
- **Отсутствие CSRF.** Для token API на Sanctum это корректно.
- **`orderByRaw('starts_at DESC')`.** В строку не подставляются пользовательские данные, инъекции нет.
- **`response()->noContent()`.** 204 после удаления — корректный код.
- **Нет ограничений на прошлые и будущие даты.** Это соответствует условию «других ограничений на даты нет».
- **Нет метода `update`, hard delete.** Не требуются заданием.
- **Сидирование токенов через `hash('sha256', $token)`.** Sanctum хранит именно SHA-256 хеш plain-text токена, сидер корректен.
- **`Carbon::parse` для ISO 8601 со смещением.** Сам по себе парсинг корректен, смещение сохраняется; проблема только в том, что его не переводят в таймзону офиса и не нормализуют перед SQL.
- **`shouldRenderJsonWhen()`.** Настройка сама по себе правильная и покрывает большинство исключений; она не помогает только с редиректом в `Authenticate` (M6).
- **Проверка конфликта без фильтра по датам.** Прошлые брони тоже блокируют слот — это не противоречит заданию, ограничений на даты нет.
